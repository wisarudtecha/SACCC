### Editable Area Boundaries on Organization Areas

**Spending Hour:** 5 hr.

**Activity**
- เพิ่มความสามารถให้กรอกและแก้ไขขอบเขต (map boundary) ของประเทศ จังหวัด และอำเภอ ได้โดยตรงบนฟอร์มในหน้า Area Management เดิมที่ขอบเขตมาได้ทางเดียวคือผ่านแม่แบบพื้นที่ (area template) เท่านั้น
- เพิ่มฟิลด์ shape area, shape length และ year of data สำหรับระดับประเทศ พร้อมขยายชนิดฟิลด์ของฟอร์ม (AreaFormModal) ให้รองรับ number/textarea และข้อความ hint ใต้ช่อง
- เพิ่ม validation ของค่าขอบเขตก่อนบันทึก เพื่อให้ค่าที่รูปแบบไม่ถูกต้องแจ้งเตือนที่ฟอร์มแทนที่จะไปพลาดตอนบันทึก
- เพิ่มยูทิลิตี `toCoordinatesPayload` ที่ใช้ร่วมกันทั้งฝั่ง org area และ area template เพื่อจัดการความต่างระหว่าง "ไม่ได้แก้" (ส่งค่าขอบเขตเดิมกลับไป ไม่ให้ถูกล้าง) กับ "ล้างค่า" (ส่ง array ว่าง)
- เพิ่ม endpoint สำหรับอ่านข้อมูลรายตัว (country/province/district by id) ทั้งฝั่ง REST และ mapping GraphQL
- แสดงป้ายที่มา (provenance) บนรายการพื้นที่ ระบุว่าประเทศใดถูกสร้างหรือซิงก์มาจากแม่แบบใด เพื่อแยกพื้นที่ที่สร้างเองกับพื้นที่ที่มาจากแม่แบบ
- อัปเดตคำแปลไทย/อังกฤษ/จีน และปรับไฟล์ตัวอย่าง (areaCURL.sh) ให้ตรงกับ payload ใหม่

**Scope / Context**
- อยู่ในโมดูล System Configuration ส่วน Area Management (CMS) ต่อยอดจากงานแม่แบบพื้นที่ก่อนหน้า โดยเปิดให้พื้นที่ขององค์กรมี geometry ของตัวเองได้โดยไม่ต้องผูกกับแม่แบบ
- หมายเหตุการออกแบบ: การส่ง coordinates เป็น array ว่างเพื่อ "ล้าง" ยังเป็นสมมติฐานที่ยังไม่ยืนยันกับ backend จึงจำกัดไว้ในจุดเดียว (`toCoordinatesPayload`) และฟิลด์ postcode ของอำเภอฝั่ง org ยังเป็น read-only ตาม input ของ backend

**Outcome**
- ผู้ดูแลสามารถกำหนด/แก้ไขขอบเขตและข้อมูลรูปทรงของพื้นที่ระดับองค์กรได้เองบนฟอร์ม การแก้ไขที่ไม่แตะขอบเขตจะไม่ทำให้ขอบเขตเดิมหาย และการเว้นว่างถือว่าไม่มีขอบเขต
- รายการพื้นที่แสดงชัดเจนขึ้นว่าประเทศใดมาจากแม่แบบ ช่วยแยกแยะข้อมูลที่สร้างเองกับที่รับมา ตรวจสอบแล้วว่าโปรเจกต์ผ่าน type check (`tsc -b`) สำเร็จ พร้อมอัปเดตบันทึกการเปลี่ยนแปลงเป็นเวอร์ชัน 0.56.0

**Activity**

- ปรับโครงสร้างการกำหนดค่าระดับพื้นที่ (level table) ให้รองรับสองชุดชั้นข้อมูลที่ไม่เหมือนกัน คือ country → province → district ของข้อมูลองค์กร และ province → district → subdistrict ของไฟล์ตัวอย่าง โดยย้ายทุกอย่างที่ผูกกับชื่อระดับไปไว้ในตารางเดียว ทั้ง label i18n ระดับที่เปิดแสดงเป็นค่าเริ่มต้น น้ำหนักเส้นและสีพื้น รวมถึงลำดับการวาด

- ปรับ layer hook ให้รองรับการโหลดข้อมูลแบบ asynchronous พร้อมจัดการ cancellation ตอน unmount และทำ reference counting ของ URL ข้อมูลชั่วคราว เพื่อไม่ให้ข้อมูลขอบเขตค้างในหน่วยความจำเมื่อมีแผนที่หลายตัวบนหน้าจอเดียวกัน
- กรองพื้นที่ที่ถูกปิดใช้งาน (inactive) ออกจากทั้งแผนที่และรายการตัวเลือก และเพิ่มการล้าง cache ขอบเขตเมื่อมีการแก้ไขข้อมูลพื้นที่ เพื่อให้แผนที่แสดงรูปทรงใหม่โดยไม่ต้อง reload ทั้งหน้า
- อัปเดตคำแปลไทย อังกฤษ และจีน สำหรับชั้นข้อมูลระดับประเทศที่เพิ่มเข้ามา

**Scope / Context**
- อยู่ในโมดูล CMS ส่วนแผนที่ของเคส (case map) ซึ่งเดิมออกแบบ interface ไว้ให้สลับแหล่งข้อมูลได้อยู่แล้ว รอบนี้คือการเติมฝั่ง implementation ที่อ่านจากข้อมูลพื้นที่ขององค์กรจริง ต่อยอดจากงาน Area Management และ Area Template ที่ทำมาก่อนหน้า
- ข้อจำกัดจากฝั่ง backend ที่ยังต้องแก้ปัญหาไว้ในโค้ดและควรแจ้งทีม backend ได้แก่ ข้อมูลพื้นที่ยังไม่มีชื่อภาษาจีน (ใช้ชื่อภาษาอังกฤษแทนไปก่อน) และโครงสร้าง coordinates ปัจจุบันยังไม่รองรับพื้นที่ที่แยกเป็นหลายส่วน เช่น จังหวัดที่มีเกาะ

### Conclusive API Failure Handling

**Activity**

- แก้ตัวตรวจสอบผลลัพธ์ฝั่ง CMS ที่เดิมอ่านรหัสความล้มเหลวเป็นสำเร็จ เพราะตรวจเพียงว่ามีค่าหรือไม่ ทำให้ขึ้นข้อความสำเร็จทับการบันทึกที่ถูกปฏิเสธ
- เพิ่ม guard สำหรับตรวจรูปร่างของข้อมูลแทนการตรวจว่ามีค่าหรือไม่ เนื่องจากชั้น normalize แปลง payload ว่างให้เป็น array ว่าง ซึ่งถูกมองว่ามีค่า
- บันทึกสัญญาการทำงานใหม่นี้ไว้ใน CLAUDE.md และเพิ่มเอกสารวิเคราะห์ปัญหาไว้ใน explanation log

**Scope / Context**
- อยู่ในโมดูล core ชั้น API ที่ทุกฟีเจอร์ใช้ร่วมกัน ปัญหาเดิมคือ backend ตอบการปฏิเสธด้วย HTTP 200 ทำให้ฝั่ง frontend มองว่าสำเร็จ กระทบทั้งการบันทึกโน้ตลูกค้า การผูกบัญชี social ของลูกค้า และการอ่านโครงสร้างพื้นที่
- เป็นการรวมศูนย์ logic ที่เดิมกระจายอยู่ตามหน้าจอและตรวจไม่ตรงกัน มาไว้ที่ชั้น API ชั้นเดียว

**Outcome**
- การกระทำที่ถูก backend ปฏิเสธถูกรายงานเป็นความล้มเหลวที่หน้าจอ แทนที่จะขึ้นข้อความสำเร็จแล้วล้างข้อมูลที่ผู้ใช้กรอกทิ้ง
- endpoint ที่ไม่ได้ส่งฟิลด์สถานะยังทำงานเหมือนเดิมทุกประการ ไม่มี regression ในส่วนที่ไม่เกี่ยวข้อง
- มีจุดเดียวที่ตัดสินความสำเร็จหรือล้มเหลวของ API ทำให้หน้าจอที่จะเขียนต่อจากนี้ไม่ต้องตรวจซ้ำเองอีก

- แก้ปัญหาค่า SLA ที่เป็นศูนย์หายไปตลอดเส้นทางข้อมูล ทั้งตอนอ่านค่ามาแสดงในฟอร์ม ตอนรับค่ารวมจาก workflow ที่เลือก และตอนส่งค่ากลับไปบันทึก โดยเปลี่ยนจากการตรวจว่ามีค่าหรือไม่ด้วยความเป็นจริงเชิงตรรกะ มาเป็นการตรวจว่าเป็นค่าว่างจริงหรือไม่ และกำหนดค่าเริ่มต้นตอนส่งให้ไม่เป็นสตริงว่าง เพราะตัวแปลงข้อมูลฝั่ง GraphQL จะตัดฟิลด์ที่เป็นสตริงว่างออกจาก input
- เพิ่มการป้องกันไม่ให้ effect ที่อ่านค่า SLA จาก workflow ไปทับค่าที่เพิ่งโหลดมาจาก record ที่กำลังแก้ไข ในจังหวะที่ยังไม่มีการเลือก workflow
- แก้ปัญหา dialog ยืนยันไม่ปิดหลังบันทึกสำเร็จ โดยให้ส่วน cleanup ปิด flag ของ dialog ทุกตัวที่ flow อาจเปิดไว้ ไม่ใช่เฉพาะตัวที่ปุ่มนั้นอยู่
- แก้กรณีกรอกข้อมูลไม่ครบแล้วกดยืนยันแล้วไม่มีอะไรเกิดขึ้น เพราะข้อความแจ้งเตือนแสดงอยู่ในฟอร์มที่ถูกปิดไปแล้วและซ่อนอยู่หลัง dialog ยืนยัน ปรับให้ย้อนกลับไปเปิดฟอร์มที่แสดงข้อความนั้นได้
- ปิดการกดปุ่มยืนยันของ sub-type ระหว่างกำลังบันทึก เพื่อไม่ให้ส่งข้อมูลซ้ำ

**Scope / Context**
- อยู่ในโมดูล CMS ส่วน System Configuration หน้า Service Management ต่อเนื่องจากงานปรับการรีเฟรชรายการบริการเมื่อวันพุธ
- SLA เท่ากับศูนย์เป็นค่าที่มีความหมายจริงในทางธุรกิจ ไม่ใช่การไม่ได้กรอก workflow ที่ไม่มีขั้นตอนกำหนดเวลาจะรายงานค่ารวมเป็นศูนย์ตามปกติ
- flow แบบสองขั้นที่แยก flag ของฟอร์มกับ dialog ยืนยันออกจากกัน ทำให้ handler ทำงานอยู่คนละขั้นกับปุ่มที่เรียกมัน ใช้หน้าจอจัดการประเภทนัดหมายเป็นแบบอ้างอิงเพราะจัดการ flag ทั้งสองไว้ถูกต้องอยู่แล้ว
- บันทึกบทเรียนเรื่องการปิด dialog ตามสถานะที่แสดงอยู่จริง และเรื่องคำสั่ง return ที่วางก่อน try จะข้ามส่วน cleanup ไว้ในเอกสาร anti-regression

**Outcome**
- ประเภทบริการย่อยที่กำหนด SLA เป็นศูนย์เก็บค่าได้ถูกต้อง ทั้งตอนบันทึกและตอนเปิดกลับมาแก้ไข
- dialog ยืนยันปิดเองหลังบันทึกสำเร็จ ผู้ใช้ไม่ต้องปิดเองอีกต่อไป
- กรณีกรอกข้อมูลไม่ครบ ผู้ใช้เห็นว่าฟิลด์ใดมีปัญหาแทนที่จะกดยืนยันแล้วไม่มีอะไรเกิดขึ้นและออกจากสถานะนั้นไม่ได้นอกจากกดยกเลิก

### React Router Duplicate Instance Resolution

**Spending Hour:** 2 hr.

**Activity**
- ไล่หาสาเหตุที่หน้าบทความในโมดูล KMS ขึ้น error ว่าใช้ hook ของ router นอก provider ทั้งที่ provider ครอบทั้งแอปอยู่แล้ว พบว่ามี package ของ router สองชุดถูกโหลดพร้อมกัน ชุดหนึ่งเป็นไดเรกทอรีที่ค้างมาจากการติดตั้งด้วย package manager ตัวเก่า อีกชุดเป็นตัวที่ผูกกับ router เวอร์ชันปัจจุบันอย่างถูกต้อง
- พบว่ามีไฟล์ 16 ไฟล์ import จาก package ที่ไม่เคยถูกประกาศไว้ใน manifest ของโปรเจกต์ จึง resolve ไปที่ไดเรกทอรีที่ค้างอยู่ ทำให้ provider กับ hook อ่าน context คนละตัวกัน
- แก้โดยประกาศ package ใน manifest ให้ตรงกับเวอร์ชันที่ router ปัจจุบันผูกไว้ พร้อมตั้งค่า dedupe ใน build config เพื่อบังคับให้เหลือชุดเดียวในกราฟ และล้าง cache ของ dependency ที่ build tool เก็บไว้ เพราะ cache จะยังจ่ายชุดเดิมต่อแม้แก้ที่ต้นทางแล้ว
- บันทึกวิธีตรวจสอบไว้ในเอกสาร anti-regression ว่า error ลักษณะ "ใช้งานนอก provider" ของไลบรารีที่ทำงานด้วย context ให้ตรวจว่ามี package ซ้ำก่อนไล่ดูโครงสร้างคอมโพเนนต์

**Scope / Context**
- กระทบโมดูล KMS ที่ผู้ใช้เจอปัญหาโดยตรง แต่ต้นเหตุอยู่ที่ระดับ dependency ของทั้งโปรเจกต์ จึงแก้ที่ manifest และ build config
- ข้อความ error ชี้ไปที่คอมโพเนนต์ซึ่งอยู่ลึกเข้าไปหลายชั้นใต้ provider จึงทำให้เข้าใจผิดว่าเป็นปัญหาการวางโครงสร้างหน้าจอ ทั้งที่ไม่มีอะไรถูก render อยู่นอก provider เลย
- การ import จาก package ที่ไม่ได้ประกาศใน manifest ทำงานได้ด้วยความบังเอิญของการวาง dependency เท่านั้น ไม่ใช่พฤติกรรมที่รับประกันได้

**Outcome**
- หน้าบทความในโมดูล KMS เปิดใช้งานได้ตามปกติ จากเดิมที่เข้าไม่ได้เลย
- ขนาด bundle ของ router ที่ต้องดาวน์โหลดลดลงอย่างมีนัยสำคัญ เพราะเหลือชุดเดียวและใช้ chunk ร่วมกัน จากเดิมที่โหลดสองชุดแยกกัน
- โครงสร้าง dependency ของ router ถูกประกาศไว้ชัดเจน ปัญหาเดิมจะไม่กลับมาเงียบ ๆ จากการติดตั้งครั้งถัดไป

**Daily Estimated Effort:** 8 hr. / 8 hr.
