**Outcome**
- ผู้ใช้เห็นรายการเคสที่เชื่อมโยงครบถ้วนตรงกับข้อมูลจริงบนเซิร์ฟเวอร์ทุกอุปกรณ์ ไม่ขึ้นกับ cache ในเครื่อง

### GraphQL Case-Update Input Sanitizing

**Spending Hour:** 3 hr.

**Activity**
- ขยายความสามารถของชั้นแปลง REST → GraphQL ให้รองรับการตัด field ที่ input type ของเซิร์ฟเวอร์ไม่รับ ออกจาก mutation body ก่อนส่ง (`omitInputFields`) ทั้งระดับ top-level และระดับ nested (เช่น field ภายในแต่ละ attachment) โดยกำหนดไว้ในที่เดียวต่อ endpoint ครอบคลุมทุก call site
- กำหนดรายการ field ที่ต้องตัดสำหรับ endpoint อัปเดตเคส: `customerId` (การผูกลูกค้ามี mutation ของตัวเอง), `docId` (เลขเอกสารที่ server กำหนดเอง) และ field audit ภายใน attachments (orgId, caseId, created/updated at/by) ซึ่ง attachment input ฝั่ง server รับเฉพาะ id/type/attId/attName/attUrl
- แก้ flow เชื่อม/ยกเลิกเชื่อมโยงเคสให้แปลง `caseSla` เป็น string ตาม input type ก่อนส่ง และยกเว้น `referCaseId` ไม่ให้ถูกตัดทิ้งเมื่อเป็นค่าว่าง เพราะการยกเลิกเชื่อมโยงสื่อด้วย empty string
- เพิ่ม unit tests ครอบคลุมสัญญาการ sanitize ของ case-update: ตัด field ที่ไม่รับทั้ง top-level และ nested, คงเนื้อหา attachment ไว้ครบ, และคง `referCaseId: ""` สำหรับการ unlink

**Scope / Context**
- องค์กรที่เปิดโหมด GraphQL (`VITE_USE_GRAPHQL=true`) บันทึกเคสไม่ได้ โดน `BAD_USER_INPUT` เพราะ body ที่ส่งถูก spread มาจาก read model ของเคส ซึ่งมี field มากกว่าที่ input type ของ mutation กำหนด — และ read model ฝั่ง BFF ยังโตเรื่อย ๆ (`docId` เพิ่งปรากฏ) ทำให้ payload ที่เคยผ่านกลับมา fail ได้โดย frontend ไม่ได้แก้อะไรเลย
- อีกปัญหาคือการ unlink เคสเงียบ ๆ ไม่ทำงานในโหมดนี้ เพราะชั้นแปลงตัด empty string ทิ้ง ทำให้ `referCaseId: ""` ไม่เคยถึงเซิร์ฟเวอร์
- เลือกใช้ omit-list แทน pick-list โดยเจตนา: ถ้า field ใหม่โผล่มา omit-list จะ fail แบบมี error บอกชื่อ field (แก้ได้ทันที) ส่วน pick-list จะตัด field ที่ถูกต้องทิ้งเงียบ ๆ เสี่ยงข้อมูลหาย

**Outcome**
- การบันทึกเคส (รวมถึงปิดเคสที่มีไฟล์แนบ) และการเชื่อม/ยกเลิกเชื่อมโยงเคสทำงานได้ปกติในโหมด GraphQL ทุก call site ของ endpoint เดียวกันได้รับการแก้พร้อมกันเพราะกฎอยู่ที่ config ของ endpoint ไม่ใช่กระจายตามจุดเรียก
- REST mode ไม่ได้รับผลกระทบ การตัด field เกิดเฉพาะชั้นแปลง GraphQL
- ตรวจสอบด้วย `tsc -b` (ผ่าน) และ `vitest` (264 tests ผ่านทั้งหมด) ก่อน commit

### Linked Cases Resilience for Unavailable Case Details

**Spending Hour:** 3.5 hr.

**Activity**
- เปลี่ยนแท็บ Linked Cases ให้ดึงรายละเอียดของเคสที่เชื่อมโยงแต่ละเคสผ่าน endpoint ข้อมูล SOP (ตัวเดียวกับที่หน้ารายละเอียดเคสใช้) แทน endpoint lookup เดิมที่ไม่ให้ข้อมูลเคสสถานะปลายทาง (cancelled/closed)
- เปลี่ยนการดึงหลายเคสพร้อมกันจาก `Promise.all` เป็น `Promise.allSettled` พร้อมฟังก์ชันแยกผลลัพธ์ (loaded / failed ids) เพื่อไม่ให้เคสเดียวที่โหลดไม่ได้ทำให้ทั้งลิสต์ว่าง
- เพิ่มการ์ดรูปแบบย่อ "ไม่สามารถโหลดรายละเอียดได้" สำหรับเคสที่ยังเชื่อมโยงอยู่แต่ดึงรายละเอียดไม่สำเร็จ โดยการ์ดยังคลิกเปิดเคสและยกเลิกเชื่อมโยงได้ตามปกติ ทั้งสำหรับเคสลูกและเคสแม่
- เพิ่มข้อความแปลของการ์ดรูปแบบย่อใน i18n ทั้ง 3 ภาษา (en/th/cn) และ unit tests สำหรับตัวแยกผลลัพธ์ (สำเร็จทั้งหมด / บางส่วน fail / สำเร็จแต่ไม่มีข้อมูล)

**Scope / Context**
- ต่อเนื่องจากงาน Linked Cases เมื่อวาน: เมื่อเชื่อมโยงเคสที่ถูกยกเลิก (cancelled) แล้วลิสต์เคสที่เชื่อมโยงแสดงว่างเปล่า เหมือนการเชื่อมโยงไม่สำเร็จ ทั้งที่ server บันทึกความเชื่อมโยงไว้แล้ว สาเหตุคือ endpoint lookup เดิมไม่ให้ข้อมูลเคสสถานะปลายทาง และ `Promise.all` fail-fast ทำให้เคสที่โหลดสำเร็จหายไปด้วย
- หลักการสำคัญ: id ที่ server ส่งมาใน `referCaseLists` เป็นหลักฐานว่าความเชื่อมโยงมีอยู่จริง UI จึงต้องไม่ลบเคสนั้นออกจากลิสต์เงียบ ๆ เพียงเพราะ lookup รายละเอียดไม่สำเร็จ

**Outcome**
- รายการเคสที่เชื่อมโยงแสดงครบตรงกับข้อมูลจริงบน server เสมอ ไม่ว่าเคสใดเคสหนึ่งจะดึงรายละเอียดได้หรือไม่
- เคสที่โหลดรายละเอียดไม่ได้ยังคงเปิดดูและยกเลิกเชื่อมโยงได้จากแท็บนี้ ผู้ใช้ไม่สับสนว่าความเชื่อมโยงหายไป
- ตรวจสอบด้วย `tsc -b` (ผ่าน) และ `vitest` (264 tests ผ่านทั้งหมด) ก่อน commit

### Anti-Regression Skill Restructure and New Lessons

**Spending Hour:** 1.5 hr.

**Activity**
- จัดโครงสร้าง anti-regression skill ใหม่ทั้งไฟล์ จากข้อความกฎสั้น ๆ เป็น skill เต็มรูปแบบ: ขั้นตอนก่อนเริ่มงาน, วิธีระบุความผิดพลาด, หา root cause, สกัดบทเรียนที่ใช้ซ้ำได้, แปลงเป็น Prevention Rule ที่บังคับใช้ได้, ตรวจซ้ำกับบทเรียนเดิม และ Operating Rules
- บันทึกบทเรียนใหม่ 3 ข้อจากงาน GraphQL sanitizing และ Linked Cases: (1) read model ที่ผ่าน type-check อาจยังไม่ผ่าน input validation ของ GraphQL (2) input type เข้มงวดทุกระดับ nesting และ read model ฝั่ง server เติบโตตลอด ต้องจัดการที่ config ของ endpoint ที่เดียว (3) `Promise.all` ที่ fan-out ตาม id list ทำลิสต์ว่างทั้งก้อนเมื่อ record เดียว fail และต้องเลือก lookup endpoint ตามสถานะ record ที่ endpoint นั้นให้ข้อมูล
- ปรับ `CODEBUDDY.md`: เพิ่มส่วน Workflow ก่อนสร้าง/แก้โค้ด, อัปเดต path ของ anti-regression skill, ปรับคำอธิบาย Vitest และเพิ่มคำสั่งรัน test เดี่ยว พร้อมจัดรูปแบบ `LICENSE.md`/`README.md` เล็กน้อย

**Scope / Context**
- ตามกฎของโปรเจกต์ ทุกความผิดพลาดต้องกลายเป็นกฎที่ใช้ซ้ำได้ งานแก้ GraphQL validation และลิสต์เคสที่เชื่อมโยงของวันนี้มี failure pattern ที่น่าจะซ้ำได้ใน endpoint/ฟีเจอร์อื่น จึงบันทึกไว้พร้อมวิธีป้องกัน
- โครงสร้าง skill เดิมเป็นเพียงข้อความกฎสั้น ไม่มี frontmatter และขั้นตอนปฏิบัติ ทำให้นำไปใช้ก่อนเริ่มงานได้ยาก

**Outcome**
- บทเรียนใหม่ 3 ข้อพร้อม root cause และ Prevention Rule ถูกบันทึกเป็นเอกสารถาวร และ skill มีโครงสร้างที่นำไปใช้ตรวจก่อนทำงานลักษณะเดียวกันได้จริง

**Daily Estimated Effort:** 8 hr.
