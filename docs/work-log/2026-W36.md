**Scope / Context**
- อยู่ในโมดูล CMS ส่วนแผนที่ทั้งหมด ได้แก่ การเลือกที่อยู่ตอนสร้างเคส แผนที่ในหน้ารายละเอียดเคส แผนที่ติดตามเจ้าหน้าที่ และหน้าวาดขอบเขตพื้นที่ในส่วนตั้งค่าระบบ
- ที่มาของงานคือ API key ของ ArcGIS ถูกจำกัดโดเมนไว้ และ build ของ qa/sit/production ไม่มี key ติดไปด้วย ทำให้ basemap ตกไปใช้ tile รุ่นเก่าและการค้นหาที่อยู่กับการคำนวณเส้นทางใช้งานไม่ได้ จึงต้องมีทางเลือกผู้ให้บริการรายที่สองที่รองรับข้อมูลไทยได้ดี
- เลือกวิธีสลับผู้ให้บริการตอน build และโหลดเฉพาะ SDK ของผู้ให้บริการที่เลือก เพราะถ้า import ทั้งสองไว้ในไฟล์เดียวกัน bundle ของสภาพแวดล้อมที่เลือก Longdo จะยังต้องดาวน์โหลด SDK ของ ArcGIS ซึ่งเป็นก้อนที่ใหญ่ที่สุดของแอปอยู่ดี
- ผลจาก spike เปลี่ยนแผนงานส่วนเส้นทาง เพราะ API เส้นทางของ Longdo ส่งกลับมาเฉพาะคำแนะนำการเดินทาง ระยะทาง และเวลา แต่ไม่มีข้อมูลรูปเส้นสำหรับวาดบนแผนที่ จึงย้ายส่วนนั้นไปทำทีหลังด้วยวิธีอื่น
- ค่าเริ่มต้นยังเป็น ArcGIS และยังไม่มีสภาพแวดล้อมใดถูกสลับไปใช้ Longdo งานส่วนนี้จึงยังไม่มีผลต่อผู้ใช้

**Outcome**
- แผนที่ทั้งสี่จุดในระบบพูดกับชนิดข้อมูลกลางแทนคลาสของ ArcGIS โดยตรงแล้ว การเพิ่มผู้ให้บริการรายใหม่ไม่ต้องแก้ทุกจุดที่เรียกใช้อีกต่อไป
- มีแผนที่ Longdo พร้อมการค้นหาสถานที่และการแสดงขอบเขตการปกครองใช้งานได้แล้วเมื่อตั้งค่าให้เลือกผู้ให้บริการรายนี้
- สภาพแวดล้อมที่เลือก Longdo จะไม่ดาวน์โหลด SDK ของ ArcGIS เลย (ยังไม่ได้วัดขนาด bundle จริง)
- ไฟล์เดิมที่ถูกแก้มีจำนวนบรรทัดลดลงสุทธิ เพราะตรรกะที่ย้ายออกไปอยู่ใน service และแค็ตตาล็อก basemap แทนที่จะกระจายอยู่ในคอมโพเนนต์แผนที่
- งานยังไม่จบ ส่วน overlay เจ้าหน้าที่ เส้นทาง หน้าวาดขอบเขต และการตั้งค่าสภาพแวดล้อม ยังค้างอยู่ จึงยังไม่ commit เข้า repository ในรอบนี้

- รื้อคอมโพเนนต์แผนที่ฝั่ง ArcGIS ให้ผูกกับชนิดข้อมูลกลางแทนคลาสของ SDK ย้ายนิยาม prop ทั้งหมดไปไว้ในไฟล์ชนิดข้อมูลร่วม ย้ายการเรียก reverse geocode ไปใช้ service แยก และย้ายส่วนสร้าง basemap ของ ArcGIS ออกไปไฟล์เฉพาะผู้ให้บริการ เหลือแค็ตตาล็อก basemap กลางที่ไม่ import SDK ใด ๆ

- ย้ายฟังก์ชัน ringsSignature ซึ่งเป็น helper บริสุทธิ์ออกจากไฟล์ที่ import SDK ของ ArcGIS ไปไว้รวมกับ helper เรขาคณิตอื่นใน utils แล้วให้ sketch layer ทั้งสองฝั่งเรียกจากที่เดียวกัน เพราะการ import จากไฟล์เดิมดึง Esri geometry ~185KB เข้าไปอยู่ใน bundle ของ Longdo โดยไม่จำเป็น บันทึกเป็นกฎ anti-regression ว่าการ import binding เดียวจากโมดูลก็ยังลากทั้ง import graph ของโมดูลนั้นมาด้วย
- ปรับตำแหน่งการ์ดพิกัด/ที่อยู่บนแผนที่ใหญ่ให้ไม่ทับแถบเครดิตผู้ให้บริการที่ SDK วาดชิดขอบล่าง

- เพิ่มคำแปลที่เกี่ยวกับการค้นหาสถานที่บนแผนที่ครบทั้งสามภาษา
- ตรวจ tsc ทั้ง repo ผ่านสะอาดแล้วจึง commit งานแผนที่ทั้งก้อนเข้า repository (งานส่วนนี้ค้างมาตั้งแต่วันจันทร์เพราะยัง build ไม่ผ่าน)

**Scope / Context**

- ค่าเริ่มต้นยังเป็น ArcGIS และยังไม่มีสภาพแวดล้อมใดสลับไปใช้ Longdo งานส่วนนี้จึงยังไม่มีผลต่อผู้ใช้

**Outcome**

### Service Type Price and Screen Improvements

**Activity**

- เพิ่มคอลัมน์สถานะ active/inactive ในรายการ และปุ่ม toggle สถานะในฟอร์ม
- เปิดการอัปโหลดรูปแนบของประเภทบริการกลับมา และกำหนด path การอัปโหลดเป็น service เพิ่ม mapping ฝั่ง GraphQL ให้ path นี้ไปที่ operation ของ CRM เพื่อตัด warning ตอน dev
- เพิ่ม dialog ยืนยันก่อนสร้างหรือแก้ไข โดยฟอร์มจะพัก payload ไว้ก่อน แล้วยิง mutation หลังผู้ใช้กดยืนยัน
- แก้การส่งข้อมูลตอนแก้ไขให้ระบุ record ด้วย identifier ที่ API ต้องการ (ค่า UUID ของ serviceId ไม่ใช่ integer PK) รูปแบบเดียวกับที่แก้ให้ appointment type ก่อนหน้านี้
- ปรับการอ่านสถานะผลลัพธ์จาก envelope ที่ส่ง status มาเป็นสตริง "0"/"-1" และดึงข้อความจาก field message/desc/msg ให้ครบทั้งกรณีสำเร็จและล้มเหลว

- เพิ่ม stub แบบ deterministic (hash จาก unitId) หลัง `VITE_MOCK_API` เพื่อให้สร้างและ demo คอลัมน์ workload กับการจัดลำดับ Recommend ได้ก่อน backend จะพร้อม โดย component เรียกใช้เหมือนกันทั้งสองโหมด
- เพิ่มคำแปลของ label คอลัมน์ใหม่และข้อความ error ครบทั้งสามภาษา

**Scope / Context**
- อยู่ในโมดูล CMS หน้าต่างมอบหมายเจ้าหน้าที่เข้าเคส (`singleAssignOfficer.tsx`)
- เป็นงานฝั่ง frontend ที่ทำล่วงหน้าก่อน backend: endpoint `POST /units/workload` ยังไม่มีในระบบจริง ข้อมูล workload กับ assigned cases จึงมาจาก stub เมื่อเปิด mock mode และในสภาพแวดล้อมจริงเซลล์สองตัวนี้จะแสดงสถานะ "retry" จนกว่า backend จะพร้อม ส่วน ETA/TTL ใช้ routing provider ที่มีอยู่แล้วจึงทำงานได้จริง
- เหตุผลของงานคือ dispatcher ต้องเห็นภาระงานของแต่ละเจ้าหน้าที่และระยะเวลาเดินทางถึงจุดเกิดเหตุ ก่อนตัดสินใจมอบหมาย
- ยังไม่ลง changelog เพราะสองในสามคอลัมน์ยังไม่มีข้อมูลจริงในสภาพแวดล้อมที่ใช้งาน เหตุผลเดียวกับที่งานเพิ่ม map provider ก่อนหน้ายังไม่ลง changelog

**Outcome**

- โครงฝั่ง frontend พร้อมเชื่อม backend ทันทีที่ `POST /units/workload` ขึ้น โดยไม่ต้องแก้ component (แค่ปิด mock flag)
- ความล้มเหลวของการดึงข้อมูล workload ถูกจำกัดอยู่เฉพาะเซลล์ที่เกี่ยวข้อง roster และการมอบหมายงานยังทำงานได้ตามปกติ

### Incident Location to Service Center Auto-Match

**Spending Hour:** 4 hr.

**Activity**
- ทำการจับคู่จุดเกิดเหตุกับพื้นที่รับผิดชอบ (Service Center) ตอนสร้างเคส โดยทดสอบพิกัดของหมุดจุดเกิดเหตุกับ polygon ระดับอำเภอของแต่ละพื้นที่ ถ้าจุดตกอยู่ในอำเภอเดียวแบบไม่กำกวม จะเลือกพื้นที่รับผิดชอบนั้นให้อัตโนมัติและล็อกฟิลด์ตลอด flow การสร้าง พร้อมข้อความอธิบายว่าระบบเลือกให้ ถ้าไม่ตกในพื้นที่ใดเลยหรือคาบเกี่ยวมากกว่าหนึ่ง จะปล่อยให้เลือกเองและวาดวงกลมรัศมีรอบหมุดเป็นตัวช่วยตัดสินใจ
- เขียน helper แบบไม่ผูก SDK สองตัว: `isPointInPolygon` (ray casting รองรับ hole) และ `generateIncidentCircleRing` (สร้างวงกลม geodesic ด้วย haversine forward formula ให้สเกลตรงที่ละติจูดของไทย) ให้ทั้งสาม map provider ใช้ร่วมกัน แยกตรรกะการตัดสินใจ match ออกเป็น pure function `resolveServiceCenterMatch` ที่เทสต์ได้โดยไม่ต้องพึ่ง React
- แยก hook `useServiceCenterMatch` ที่ดูแลส่วน async (ดึง district, สถานะ idle/loading) และ hook `useOrgIncidentRadiusMeters` ที่อ่านค่ารัศมีจาก org record โดยความล้มเหลว (route ยังไม่มีในระบบจริง, field หาย, รูปผิด) ทั้งหมด fallback เป็นค่า default 900 เมตร ไม่ throw ไม่บล็อกการ match
- เพิ่ม overlay วงกลมรัศมีให้ครบทั้งสาม provider: ArcGIS ใช้ `geometryEngine.geodesicBuffer`, Longdo และ MapTiler วาดจาก ring ที่ generate เอง (Longdo วาดใต้หมุดเคส, MapTiler ผูก source/layer กลับทุกครั้งที่ style swap) overlay เป็น non-interactive ทั้งหมด คลิกแผนที่ทะลุผ่านได้
- ร้อยพารามิเตอร์ `incidentRadius` ผ่านชั้นคอมโพเนนต์แผนที่ (`AddressMapField` -> provider maps, `BoundaryMapField`, `CaseStaffMapField`) ด้วยสัญญาเดียวกับ `boundaries`/`sketch` คือ state เป็นของชั้นบน คอมโพเนนต์แค่วาดตามที่รับมา
- ต่อ endpoint `GET /organizations/{orgId}` (getOrgSettings) และชนิด `OrgSettings` พร้อม type guard ฝั่ง core เป็นสัญญา FE ล่วงหน้า ยังไม่มีใน backend
- เพิ่ม unit test ให้กฎการ match, point-in-polygon และ geometry helper และตั้ง `tsconfig.app.json` ให้ exclude `*.test.ts`/`*.test.tsx` ไม่ให้เข้า build
- เพิ่มคำแปลข้อความ "ระบบเลือกให้อัตโนมัติ" ครบทั้งสามภาษา

**Scope / Context**
- อยู่ในโมดูล CMS ส่วนฟอร์มสร้างเคสและหน้ารายละเอียดเคส และชั้นคอมโพเนนต์แผนที่ทั้งสาม provider
- เหตุผลของงานคือลดขั้นตอนของ dispatcher: จุดเกิดเหตุส่วนใหญ่ตกอยู่ในพื้นที่รับผิดชอบเดียวชัดเจน ไม่ควรต้องเลือกเอง กรณีที่คลุมเครือจริง ๆ ค่อยให้ตัดสินใจโดยมีวงรัศมีช่วย
- การจับคู่ใช้ polygon containment เท่านั้น วงกลมรัศมีไม่มีส่วนในการ match และไม่ถูกบันทึกลงเคส
- หน้าจอ edit-after-create ล็อกฟิลด์พื้นที่รับผิดชอบอยู่แล้ว (capabilities.lockArea) การ match จึงทำเฉพาะตอน create ที่ฟิลด์ยังแก้ได้
- ค่ารัศมี fallback (900 ม.) เป็นค่าคงที่ตัวเดียว รอ backend เพิ่ม column ให้ตั้งค่าต่อ org ได้ ส่วน override ต่อ case type เป็น phase 2 ที่เลื่อนออกไปก่อน

**Outcome**
- ตอนสร้างเคส พื้นที่รับผิดชอบถูกเลือกและล็อกให้อัตโนมัติเมื่อจุดเกิดเหตุตกในอำเภอเดียว dispatcher ไม่ต้องเลือกเองในกรณีทั่วไป
- กรณีจุดเกิดเหตุไม่ตกในพื้นที่ใดหรือคาบเกี่ยว ฟิลด์ยังเลือกเองได้และมีวงกลมรัศมีช่วยประเมินความครอบคลุม แสดงบนหน้ารายละเอียดเคสที่บันทึกแล้วด้วย
- วงกลมรัศมีทำงานเหมือนกันทั้งสาม map provider และไม่ขวางการคลิกวางหมุด
- 404 จาก org-settings ที่ยังไม่มีในระบบไม่ทำให้อะไรพัง เพราะ fallback เป็น 900 เมตร
- repo type-check ผ่านทั้งก้อน มี unit test ครอบกฎการ match และ geometry helper
